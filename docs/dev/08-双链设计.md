# 双链设计（联系人 / 地点 / 账号等实体可链接）

> 本轮只出设计，不写实现。
> 目标：让「实体型块」能被正文引用，并且能反查「谁提到过它」。
> 结论先给：**用自定义 inline content（`entityRef`）+ 按「类型 + 规范化名称」生成的稳定 ID，反链用扫描 + 缓存索引**，先做联系人一个闭环。

---

## 一、目标与非目标

### 要做的

1. 正文里出现某个实体（人 / 地点 / 账号 / 纪念日…）时可以插一个**引用**，点它跳过去
2. 每个实体能看**反链**：哪几篇笔记引用了我
3. 引用在导出时能降级（Markdown / PDF 至少保留文字）

### 不做的

- 全文关系网络图、双向链接的图可视化
- 块级引用（引用一段话）
- 跨库/云端同步的实体表
- 自动 NLP 识别「小林」这类裸文本并强行建链（只做**显式引用**，避免误伤）

---

## 二、现状（已核对源码）

### 实体块有哪些、字段是什么

| 块类型 | props（`src/editor/blocks/<类型>/config.ts`） |
|---|---|
| `contact` | `name, phone, relation, email, company, title, birthday, note` |
| `location` | `name, addr, coord` |
| `account` | `site, url, user, pass, note, totp` |
| `bankcard` | `bank, no, holder, kind, theme` |
| `anniversary` | `title, date, kind, annual, remind, remindDays` |
| `bookmark` | `title, url, newTab` |
| `mood` | `emoji` |
| `voice` | `url, wave` |
| `checklist` | `items`（JSON 字符串） |

### 现有能力与缺口

- **行内内容**：`src/editor/schema.ts` 里 `inlineContentSpecs: defaultInlineContentSpecs` —— 只有默认的 text / link，**没有自定义 inline 类型**。要做引用，需要注册一个新的 inline content spec。
- **搜索**：`aggregate.ts` 的 `noteMatchesQuery()` 走 `plainTextOfBlocks()`，只取行内文本。自定义 inline 内容如果不带 `text`，搜索会搜不到 —— 必须在设计里把它当纯文本吐出来。
- **Markdown 导出**：`share.ts` 的 `inlineToMarkdown()` 只认 `link` 和普通 text；未知 inline 类型会落到 `str(n.text)`（空字符串则丢弃）——**引用会被静默丢掉**，这是必须处理的降级点。
- **PDF**：`pdfDoc.ts` 的 `toAtoms()` 只把 `link` 和 text 转成原子，未知类型同样丢失。
- **汇总页**：`collectSummary()` 是按块类型扫实体，和正文引用无关，不需要改；但「实体详情页」需要新界面。

## 三、实体归一化

### 问题

同一联系人「小林」可能出现在 3 篇笔记的 `contact` 块里，怎么判定是同一个？

### 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 实体表 | 新建 `entities` 表（SQLite）/ 对象库（IndexedDB），块里存 `entityId` | 改名、合并干净 | 要迁移现有块、要维护表、双后端各写一遍 |
| **B 稳定 key** | `entityId = 类型 + ":" + 规范化名称`（如 `contact:小林`） | 零迁移、纯函数、可离线推导 | 改名=新实体；同名不同人会撞 |
| C 手动绑定 | 用户显式把两个块「合并为同一实体」 | 最准 | 交互成本高，先不做 |

### 结论：先 B，把 A 作为后续升级路径

规范化规则（纯函数，可单测）：

1. 去首尾空白，内部连续空白压成一个
2. 全角转半角（＃→#、Ａ→A）
3. 大小写统一（拉丁字母小写；中文不动）
4. 去掉常见标点尾巴（`·`、`-`、`。`）

于是 `"小林 "`、`"小 林"`、`"小林。"` 都归一到 `contact:小林`。

**同名不同人**：先接受，UI 上在反链列表里显示「所属笔记 + 原始字段」加以区分；等真要解决时再上 A 方案（实体表 + 手动合并）。

**改名**：B 方案下改名等于换 ID，旧引用会变成「找不到的引用」。处理方式见第七节「悬空引用」。

## 四、引用语法

### 候选

| 方案 | 形态 | 优点 | 缺点 |
|---|---|---|---|
| A 自定义 inline content | `{ type: "entityRef", props: { entityId, label } }` | 结构清晰、可校验、可加图标/悬停卡 | 要写 spec + renderer + 导出降级 |
| **B link + 内部协议** | `[小林](sparrow://contact/小林)` | 零新增类型，现有导出直接可用 | 语义上冒充外链；点开要拦截；复制到外部编辑器变成怪链接 |
| C 纯文本 `@小林` 自动识别 | 文本 | 最自然 | 需要分词/识别，误伤大，且无法稳定反查 |

### 结论：A 为主，B 作为「兼容旧数据/纯文本」的降级表示

选择 A 的理由：

1. 引用是**结构**，不是链接：它要承载 entityId、可空 label、以及「目标不存在」的状态
2. 导出时可以精确降级（纯文本 + 括号），而不是抛一个外部编辑器打不开的伪协议
3. 将来要加「引用时的快照样式」「反链计数」等字段时，不用换 encode 方式

spec 草案：

```ts
// src/editor/inline/entityRef.tsx
export const EntityRef = createReactInlineContentSpec(
  {
    type: "entityRef",
    propSchema: {
      entityId: { default: "" },   // 规范化 key，如 "contact:小林"
      label: { default: "" },      // 显示名，快照；目标改名后仍可显示
      kind: { default: "contact" } // 实体类型，决定图标与跳转目标
    },
    content: "none"
  },
  {
    render: ({ inlineContent: { props } }) => <EntityChip {...props} />,
    // parse / toExternalHTML 必须给，否则粘贴与导出会丢
  }
);
```

## 五、反链索引

### 数据来源

反链 = 扫描所有笔记的块树，找 `entityRef` inline 节点（以及可选的「实体块本身」）。这和李家图的聚合一样是**纯函数**：

```ts
// src/lib/backlinks.ts
export type Backlink = {
  entityId: string;
  noteId: string;
  noteTitle: string;
  noteDate: string;
  /** 引用出现的位置（块 id + 段落序号），用于「跳到那一段」 */
  blockId: string;
};
export function collectBacklinks(notes: NoteDoc[]): Map<string, Backlink[]>;
```

### 存储策略

| 方案 | 何时算 | 成本 |
|---|---|---|
| **每次扫描**（先做这个） | 打开实体详情 / 汇总页时，`useMemo` 算一遍 | O(笔记数 × 块数)，几百篇量级可接受 |
| 增量索引 | 保存笔记时 diff 出实体引用变化，写 `backlinks` 表 | 省 CPU，但要维护一致性 |

结论：**先每次扫描**。原因是我们现在没有实体详情页的常驻需求，扫描成本远低于维护索引表的复杂度。等「反链」出现在列表里到处都要用时，再上增量索引（那时 `putNote` 已经是唯一写入口，好挂）。

### 与数据层的关系

- 不改 `NotesBackend` 接口形状（AGENTS 的硬约束）
- 反链不落盘 → 没有迁移、没有回滚问题

## 六、UI

### 正文里的引用

- 样式：纸面底 + 印章色文字 + 1px 下划虚线，前面一枚小图标（按 kind：人 / 地点 / 账号）
- 悬停：显示小卡（label + 类型 + 所在笔记 + 反链数）
- 点击：桌面进「实体详情」，移动端进同一页（同一份组件，靠 `isNarrow` 调布局）
- 目标不存在（悬空引用）：文字仍显示 `label`，但加删除线 + 提示「目标已不存在」

### 插入引用的入口

- 斜杠菜单加「引用实体」→ 弹选择器（按类型分组，可搜名称）
- 输入 `@` 触发同一个选择器（只匹配**已存在的实体**，不自动造新实体）
- 从实体块的「⋯」菜单里也能「复制引用」

### 实体详情页（新页面）

- 顶部：实体名、类型、来源块字段（电话/地址…）
- 正文：**出处**（哪个笔记的哪个块）
- 底部：**反链列表**（笔记标题 + 日期 + 一句话上下文），点进去定位到段落
- 空状态：「还没有笔记引用它」，并给一句怎么引用

## 七、与现有功能的关系

| 功能 | 影响 | 处理 |
|---|---|---|
| 搜索（`noteMatchesQuery`） | 引用不会进 `plainTextOfBlocks` | 让 inline spec 的 `toExternalHTML`/文本抽取把 `label` 当文本吐出来（改 `plainTextOfBlocks` 时识别 `entityRef`） |
| Markdown 导出 | `inlineToMarkdown` 不认 entityRef → 会被丢掉 | 显式降级成 `「label」`，若目标存在再附相对链接 |
| PDF 导出 | `toAtoms` 不认 → 丢字 | `toAtoms` 加一个分支：把 label 当普通文本原子（链接标记可选） |
| 汇总页 | 无关 | 不改 |
| 长图/打印 | 走 DOM，自动带上 chip | 不用改 |

**降级原则**：导出里永远不能丢字。引用最差退化成纯文本 label。

## 八、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 悬空引用 | 实体改名/删除后引用失效 | chip 显示 label + 删除线；提供「重新指向」入口 |
| 同名不同人 | B 方案无法区分 | 反链列表显示来源笔记；后续升级实体表 |
| 粘贴丢引用 | 复制到外部再粘回来，自定义 inline 内容可能丢 | 提供 `parse`/`toExternalHTML`，并在设计里注明「出站会降级为文本」 |
| 导出丢字 | 三处导出都要改 | 见第七节；加单测盯住「不丢字」 |
| 性能 | 每次扫描全库 | 先量：几百篇 × 每篇几十块，纯字符串遍历在毫秒级 |

## 九、分阶段计划

### P0 · 联系人闭环（2~3 天）

1. `entityRef` inline spec + chip 渲染（仅 contact）
2. 斜杠 + `@` 选择器（只列已有联系人的规范化 key）
3. `collectBacklinks()`（纯函数 + 单测）
4. 实体详情页（只读：字段 + 反链列表）
5. 三处导出降级 + 搜索取文本
6. **验收**：插一个引用 → 详情页出现该笔记；删除那篇 → 反链消失；Markdown/PDF 里文字不丢

### P1 · 铺开到其它实体（2 天）

- 地点 / 账号 / 纪念日 / 书签 接入同一套（kind 决定图标与字段展示）
- `@` 选择器分组与搜索

### P2 · 增强（可选）

- 手动合并同名实体（迁移到实体表）
- 反链的「上下文一句话」
- 未解析引用的批量修复面板

---

## 十、落地顺序建议

1. 先写 `normalizeEntityKey()` 与 `collectBacklinks()` 两个纯函数 + 单测（不碰 UI）
2. 再加 inline spec 与选择器（这一步会动 schema，风险最高，单独提交）
3. 再做详情页
4. 最后一次性补三处导出降级 + 搜索，配「不丢字」单测
