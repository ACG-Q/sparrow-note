# 表格自研方案（替代 BlockNote 表格）

> 定位：**优化项，排在最后**。本文只做设计，不改业务代码。
> 触发原因：BlockNote 自带的表格有两个我们做不到的硬限制——合并后的单元格里放不了块、表头只能一行。
> 前置阅读：`docs/dev/05-表格重构方案.md`（外层工具栏/侧栏/多选已经做完的部分）

---

## 一、目标与非目标

### 要解决的

| # | 需求 | 现在的状态 | 为什么现在做不到 |
|---|---|---|---|
| 1 | 合并单元格内插入块（图片 / 代码块 / 清单 / 语音…） | 只能写字 | 单元格内容类型是 `tableParagraph(inline*)`，结构上只装行内内容 |
| 2 | 多行表头（2~3 行） | 工具条只有 0/1 | **数据层其实支持**，是 UI 和消费方没跟上（见第二节实测） |
| 3 | 多列表头（第一列也当表头） | 有开关，但只在部分路径生效 | 同上，消费方各写各的 |

### 不做的

- 协同编辑（Yjs / 多人光标）
- 万行级大表格、虚拟滚动
- Excel 公式、条件格式、xlsx 导入导出
- 单元格内再嵌表格（嵌套深度限制 1 层）

## 二、现状核实（先摆事实，再谈方案）

### 1. 我们用的是 BlockNote 内置表格

```ts
// src/editor/NoteEditor.tsx:27
tables: { headers: true, splitCells: true },
```

### 2. 节点结构决定了单元格只能放文字

`node_modules/@blocknote/core/src/blocks/Table/block.ts`：

| 节点 | 内容规格 | 行号 |
|---|---|---|
| `table` | `tableRow+` | 160 |
| `tableRow` | `(tableCell \| tableHeader)+` | 358 |
| `tableCell` / `tableHeader` | `tableContent+` | 41 / 105 |
| `tableParagraph` | `inline*` | 305 |

`tableContent` 组里只有 `tableParagraph`，而它是 `inline*`——**单元格里永远只有段落和行内内容**，图片、代码块、清单都塞不进去。这不是配置问题，是 schema 问题。

### 3. BlockNote 的块模型本身不支持嵌套块

```ts
// node_modules/@blocknote/core/src/schema/blocks/types.ts:90
C extends "inline" | "none" | "table" | "plain"
// 紧接着的注释：
// TODO: how do you represent things that have nested content?
// e.g. tables, alerts (with title & content)
```

也就是说：**不能**通过写一个 `content: "block+"` 的自定义 BlockSpec 来绕过。想在单元格里放块，必须离开 BlockNote 的 BlockSpec，改用自定义 ProseMirror 节点。

### 4. 多行表头：数据层已经通了（实测）

`tableContent.headerRows` 是**数字**，不是布尔：

```ts
// src/schema/blocks/types.ts:353
export type TableContent<...> = {
  type: "tableContent";
  columnWidths: (number | undefined)[];
  headerRows?: number;   // ← 数字
  headerCols?: number;
  rows: { cells: TableCell<I, S>[] }[];
};
```

`blockToNode` 按这个数字逐行标记表头：

```ts
// src/api/nodeConversions/blockToNode.ts:204
const headerRows = new Array(tableContent.headerRows ?? 0).fill(true);
...
// 第 274 行
const cellNode = schema.nodes[
  isHeaderCol || isHeaderRow ? "tableHeader" : "tableCell"
].createChecked(...)
```

**实测**（`review/insert-table.mjs`）：用斜杠菜单插入一张 2×3 表 → 改存储的 `headerRows: 2` → 整页重载 → 编辑器渲染 `perRow: ["th,th,th","th,th,th"]`，`th=6 / td=0`。

**结论**：多行表头**不需要**等自研表格，一次小改造就能做。

### 5. 但消费方全都写死了「第一行」

| 位置 | 代码 | 问题 |
|---|---|---|
| 阅读模式 | `src/components/NoteReader.tsx:346` `const Cell = ri === 0 ? "th" : "td"` | 完全不看 `headerRows` 和单元格自身类型 |
| PDF | `src/lib/pdfDoc.ts:387` `headerRows > 0 && rows.length > 1 ? layoutRow(0) : null` | 跨页只重复第 0 行 |
| Markdown | `src/lib/share.ts:131` `const [head, ...body] = padded` | 只取第 0 行；GFM 本身也只支持单行表头（格式限制，不是 bug） |
| 工具条 / 侧栏 / 多选 | `TableToolbar.tsx`、`TableSideMenu.tsx:23`、`TableMultiSelect.tsx:175` | 只提供 0/1 切换 |
| 合并 | `src/editor/media/tableMerge.ts` `withHeaders()` | 只处理「有没有表头」的布尔语义 |

### 6. 选区判断：不能依赖 `instanceof`（并在本文更正一处旧结论）

`05-表格重构方案.md` 第十六节写的是「BlockNote 用的是 prosemirror-tables 的 **STC 分支**」。核实后这个说法**不准确**：

- 仓库里 `prosemirror-tables` 只有一份，版本 **1.8.5**（BlockNote 的 `package.json` 依赖 `^1.8.5`）
- BlockNote 的 dist chunk（`src-D5w0XAHX.js`）也是 `import ... from "prosemirror-tables"`，没有内联一份
- 但 `instanceof CellSelection` 实测恒为 false

所以正确表述是：**同一个包，但运行时类实例不同**（推测与 Vite 预打包 / ESM-CJS 双实例有关，尚未逐行证实）。

对方案的影响：无论原因是什么，**凡涉及跨格选区，一律用结构判断 + `forEachCell`，不要写 `instanceof`**：

```ts
export function isMultiCellSelection(sel: unknown): boolean {
  const s = sel as { $anchorCell?: unknown; from?: number; to?: number };
  return s.$anchorCell !== undefined && typeof s.from === "number" && typeof s.to === "number" && s.from !== s.to;
}
```

## 三、技术选型

| 方案 | 能解决 1（格内放块） | 能解决 2（多行表头） | 代价 | 结论 |
|---|---|---|---|---|
| **A** 继续用 BlockNote 表格，只放开 N 行表头 | ❌ 结构上无解 | ✅ 已验证可行 | 小（1~2 天） | **只做 2 的临时方案，单独排期** |
| **B** 自定义 ProseMirror 节点（不走 BlockSpec），cell 内容用 `block+` | ✅ | ✅ | 大（2~3 周） | ✅ **推荐作为自研主线** |
| **C** 完全自研编辑器层（脱离 BlockNote 文档树） | ✅ | ✅ | 极大，且和现有保存/导出/自定义块体系脱节 | ❌ 不做 |

**结论：走 B。** 理由：

1. A 在「格内放块」上无解——schema 是 `inline*`，除非改 BlockNote 源码；
2. B 可以在 BlockNote 的文档树里挂一个**自定义 Tiptap 节点**，只是这个节点不在 BlockNote 的 BlockSpec 注册表里，序列化由我们自己写；
3. C 等于重写编辑器，现有的自定义块（心情/地点/联系人…）、保存、PDF、分享全要重来，收益不匹配。

## 四、数据模型

### 新块类型：`sparrowTable`

老块保持 `type: "table"` 不动（见第七节迁移），新块：

```jsonc
{
  "id": "…",
  "type": "sparrowTable",          // 新类型，与 BlockNote 的 table 并存
  "props": {
    "headerRows": 2,               // 0..N，数字
    "headerCols": 1,
    "columnWidths": [180, 120, "auto"],
    "schemaVersion": 2,            // 便于将来再演进
    "legacy": { /* 迁移前的原 table content，出问题可回滚 */ }
  },
  "content": {
    "rows": [
      {
        "cells": [
          {
            "id": "c1",
            "colspan": 1,
            "rowspan": 1,
            "align": "left",
            "blocks": [             // ← 关键：这里是块的数组，不是行内内容
              { "type": "paragraph", "content": [{ "type": "text", "text": "季度" }] },
              { "type": "image", "props": { "url": "…" } }
            ]
          }
        ]
      }
    ]
  }
}
```

### 必须有的规范化器 `normalizeTable()`

自研后所有一致性都得自己保证，建议在任何写入路径前跑一遍：

- 补齐每行列数（按 colspan 展开后的网格宽度）
- 修 `rowspan` / `colspan` 越界与重叠
- `headerRows` / `headerCols` 夹到 `[0, 行数]` / `[0, 列数]`
- `columnWidths` 长度与网格列数对齐
- 空表 → 兜底成 1×1

配套单测（纯函数，和 `tableMerge.test.ts` 一个路子）。

## 五、NodeView 与交互

### DOM 结构

```
div.sparrow-table
  table
    colgroup > col*              ← columnWidths
    thead（headerRows 行）/ tbody
      tr
        td[colspan][rowspan]
          div.cell-body
            [子编辑器挂载点]      ← BlockNote EmbeddedEditor
```

### 关键实现点

1. **子编辑器**：每个单元格挂一个 `EmbeddedEditor`（BlockNote 提供），`initialContent` 就是该 cell 的 `blocks`，`onChange` 回写到自己节点属性。注意**不要**每次渲染重建，按 cell id 缓存实例。
2. **选区模型**：自建 `{ anchor: {row, col}, head: {row, col} }` 的矩形选区，配合一份 app 级的 `cellRange` 状态；工具条/侧栏/多选合并全部读这份状态，**不再碰 `CellSelection`**。
3. **不依赖 prosemirror-tables**：它的命令（`addRowAfter` / `mergeCells` / `splitCell`…）都假设 cell 内容是 `block+` 的特定 schema，和我们的 cell 内容不兼容；行列增删、合并拆分改写成对 `content.rows` 的纯数据操作 + 一次性 `setNodeMarkup`。
4. **撤销**：所有变更必须走 PM transaction，不要直接改 React state——否则 Ctrl+Z 断掉。
5. **粘贴**：外部 HTML 表格 → 解析成我们的 rows/cells；外部富文本进 cell 时按块拆分。
6. **移动端**：单元格里的子编辑器会带来焦点/输入法问题，需要真机验证（Android WebView 尤其）。

## 七、数据迁移

### 策略：读时兼容，写时升级

1. **读**：遇到 `type: "table"` 的老块 → 原地按老规格渲染（**只读**），不自动改写用户的存档。
2. **写**：用户第一次编辑这张表 → 转换成 `sparrowTable`：
   - 每行每列一个 cell，原来的行内内容包一层 `paragraph`
   - `headerRows` / `headerCols` 原样搬过去
   - `colspan` / `rowspan` / 对齐原样搬
   - 原始 content 存进 `props.legacy`（**回滚用**）
3. **回滚**：设置里给一个「恢复旧表格」的开关；或迁移后检测到异常（比如列宽对不上）自动降级回 `table`。
4. **种子数据 / 测试夹具**：迁移必须带单测（老 JSON → 新 JSON → 渲染出的网格等价）。

### 迁移是这次改造里最容易出事的部分

现有用户的表格都在 `type: "table"` 里，一旦写坏就是数据损坏。所以：

- 迁移函数必须是**纯函数 + 可测**；
- 迁移后立刻把 `legacy` 写进存档，别只在内存里留；
- 迁移前先备份一份（Tauri 侧可以直接复制 SQLite 文件）。

## 八、风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| BlockNote 内部 API 变动 | `EmbeddedEditor`、`BlockNoteEditor` 的 API 在 0.x 里并不稳定 | 锁版本；把耦合点收在一个 `sparrowTable/` 目录里 |
| 撤销/重做 | 自定义节点 + 子编辑器两层，transaction 容易漏 | 所有改动走一个 `applyTableOp()` 出口 |
| 性能 | 每个 cell 一个子编辑器，20×10 就是 200 个 | 懒挂载（cell 获得焦点才创建编辑器） |
| 移动端输入法 | 子编辑器嵌套 + 触摸滚动 | 真机验证，必要时只读展示 + 点开单格编辑 |
| 导出不一致 | 5 处消费方各写各的 | 先把「表格读取」抽成一个公共函数（`readTable(content)`），所有消费方都走它 |
| 迁移事故 | 见第七节 | legacy 副本 + 备份 + 单测 |

## 九、分阶段计划

### P0 · 只读渲染（不接编辑）

- 新节点 `sparrowTable` 能渲染：多行表头、colspan/rowspan、格内块（只读）
- 老 `table` 块照旧渲染
- **验收**：一篇含 2×3 合并表 + 格内图片的笔记，阅读模式/PDF/长图都能正确出图；`tsc` + 现有测试全过

### P1 · 编辑能力

- 格内子编辑器、增删行列、合并拆分、对齐、拖选多格
- 工具条/侧栏接到新节点上
- **验收**：`05` 文档里那套 9+6 项 QA 全部在新节点上复跑通过

### P2 · 高级特性

- 多行表头/多列表头的完整 UI（步进器）
- 行列拖拽排序
- 迁移开关 + 回滚
- **验收**：老笔记批量迁移后，逐条抽查 10 篇；迁移失败可一键回滚

## 十、建议的落地顺序

1. **先做「多行表头」小改造**（不用自研，1~2 天）：
   - 工具条/侧栏把表头行数放开到 1/2/3
   - 阅读模式按 `headerRows` 渲染 `th`
   - PDF 按 N 行重复表头
   - Markdown 把多行表头合并成一行
   > 依据：第二节第 4 点已经实测过，数据层天生支持。
2. **再抽公共读取函数** `readTable(content)`，让 5 个消费方统一入口——这是自研前的必要准备。
3. **最后排自研表格**（P0 → P1 → P2），风险最高的迁移放在 P2 末尾，且必须有 legacy 回滚。
